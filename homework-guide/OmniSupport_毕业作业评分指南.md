# OmniSupport 课程毕业作业评分指南

> 整理自《OmniSupport 课程毕业大作业：学员任务书与教师评分指南》。
>
> 评分顺序：**先检查硬门槛，再评基础分，最后计算可选加分；总分封顶 100 分。**

## 1. 评分原则

- 不以代码量、页面数量或架构名词多少取胜。范围小但证据完整、边界清楚、可复现的交付，优于功能很多但无法验收的 Demo。
- 所有结论必须有机器证据支撑，如 JSON、测试结果、查询结果、Trace、Manifest 或 Release 记录；截图只能作为辅助证据。
- 必须证明系统能运行、能解释、能复现、能拒答、能控制副作用、能追踪并能回滚。
- API、CLI 或 OpenAPI 能完整展示结构化“问题处理方案卡”即可通过，不强制实现完整前端。
- 可选能力不能掩盖硬门槛或基础能力缺陷。
- Deterministic fallback 可以证明降级链路可用，但不能作为真实模型生成质量的证明。

## 2. 评分流程

1. 确认学员选择的主题、基线 Commit、候选 Commit、Release、模型模式及提交物完整性。
2. 按 G1–G6 检查硬门槛，并执行必要的真实性抽查。
3. 使用 C1–C8 统一验收用例检查正常、失败、安全、回归和回滚路径。
4. 按七个评分维度给出基础分，满分 100 分。
5. 计算可选加分，最终总分仍不得超过 100 分。
6. 根据硬门槛和总分给出结论，并记录失分证据及补交要求。

## 3. 硬门槛与红线

### 3.1 硬门槛

| 编号 | 硬门槛 | 通过标准 |
|---|---|---|
| G1 | 可运行 | 助教能从仓库根目录按 README 在 Docker/Devbox 重跑；不得依赖只存在于个人机器的私有 venv。 |
| G2 | 无伪证据 | 引用来自真实检索结果；不得把手写 URL 或 `evidence_id` 伪装成检索证据。 |
| G3 | 租户与隐私 | 不跨 Tenant 返回 Case 或 Evidence；Trace 默认不记录客户原文、密钥和 PII。 |
| G4 | 无失控副作用 | 高风险动作不得自动执行；权限、审批和幂等由代码或契约保证，不能只靠 Prompt 提醒。 |
| G5 | 可回归 | 新增契约测试和单测通过，原 `scripts.capstone.verify_e2e` 仍为 `pass`。 |
| G6 | 可追溯 | 响应包含 `release_id` 和 `trace_id`；报告能从请求定位到关键 Span 与版本。 |

### 3.2 硬门槛计分规则

- **G2、G3 或 G4 失败：本次作业判为未通过，修复后可重新验收。**
- **G1、G5 或 G6 失败：总分最高 59 分，补齐证据后可恢复正常评分。**
- 加分项不得抵消任何硬门槛失败。

### 3.3 禁止做法

- 在 fallback 中写死标准答案或 citation，使回答“看起来更真”。
- 浏览器携带内部 Service Token 直接调用 Tool API，绕过 Product API 的身份与租户控制。
- 删除失败样本、只展示成功页面，或使用不同数据分别运行基线和候选版本。
- 提交真实客户数据、真实密钥、未脱敏日志或包含 PII 的 Trace。
- 将 deterministic fallback 的结果描述成真实模型生成质量。

## 4. 基础评分量表（100 分）

| 维度 | 分值 | 高质量表现 | 重点核验证据 | 典型失分 |
|---|---:|---|---|---|
| 1. 产品问题与边界 | 8 | 用户、场景、成功、拒答及动作边界清晰；非目标合理；能说明为什么不是普通聊天框。 | `architecture.md`、方案卡输出契约、主题边界案例、演示说明。 | 只写技术清单，没有真实用户问题；成功、拒答或审批边界模糊。 |
| 2. 数据、契约与幂等 | 12 | 至少 2 份合成文档；Manifest、PII、版本和失败门禁完整；重复运行不会产生重复数据。 | 文档与 Manifest、Contract Test、失败报告、两次运行计数、数据与索引 Release 绑定。 | 手工入库；没有失败输入；重跑数据翻倍；数据版本不可追溯。 |
| 3. RAG、改写与证据 | 22 | `vector_query`、`lexical_query` 和原问题分工正确；精确标识被保护；输出结构化；citation 支持结论；证据不足时澄清或拒答。 | Query Rewrite Debug、Hybrid Retrieval 结果、Evidence、Schema Test、C1–C4 原始响应与 Trace。 | 改写丢失错误码、型号或版本；引用与结论不一致；无证据仍确定作答；输出不符合 Schema。 |
| 4. Skill、Tool 与控制 | 15 | 能力用途、输入输出、失败、权限和版本可发现；最小权限；确认、HITL、幂等及审计链完整。 | Skill/能力定义、Tool 契约、`completed`/`awaiting_approval`/`resume` 证据、幂等重放和审计记录。 | 让模型自行决定是否审批；高风险动作可绕过 HITL；重复执行产生二次副作用。 |
| 5. 评测与可观测 | 18 | 基线和候选使用同一数据及口径；Golden Set 覆盖充分；报告包含失败分布；能使用 Trace 定位并修复坏案例。 | 6–8 条 Golden Set、原始评测结果、基线/候选对比、Phoenix `trace_id`、Bad-case 分析。 | 只展示一条成功回答；更换测试数据制造提升；没有失败分析或关键 Span。 |
| 6. 发布、回滚与成本 | 15 | Data、Index、Prompt、Skill、Service 版本绑定；门禁、激活、回滚和回归证据完整；性能及成本有可解释的对比。 | Release Manifest、Pointer/Audit、Dry-run、Rollback、C8、原 E2E、p50/p95、Token 或代理指标。 | 只修改配置而不记录版本；只能发布不能回滚；回滚后资产版本不一致；无性能或成本记录。 |
| 7. 工程交付与反思 | 10 | README 可复现；提交清晰；演示有效；能诚实说明本地实现与生产之间的差距及下一步验证。 | D1–D8、干净环境复跑记录、8 分钟演示、Reflection 中至少 3 个生产差距。 | 依赖口头补充；文档和代码不一致；夸大生产状态；反思只有空泛的“未来优化”。 |
| **合计** | **100** |  |  |  |

> 评分时不得因未实现非必需的 UI、新 Tool、GraphRAG、多模态或云部署而扣除基础分。

## 5. 统一验收用例

| 用例 | 输入意图 | 预期行为 | 核心证据 |
|---|---|---|---|
| C1 正常证据问答 | 问题与新增知识包直接相关 | 返回诊断、不超过 3 个步骤、至少 1 条正确 citation，并包含 `release_id`、`trace_id`。 | 回答内容与证据一致。 |
| C2 精确标识保护 | 问题包含错误码、型号或版本，如 `EG-BOOT-004` | 改写后标识仍存在；全文检索可命中；回答不篡改标识。 | Query Rewrite Debug 与 Trace。 |
| C3 歧义澄清 | 缺少产品、版本或错误信息 | `needs_clarification=true`，或执行安全拒答。 | 不把猜测包装成高置信答案。 |
| C4 证据不足或冲突 | 知识库无答案，或两份文档冲突 | citations 为空或明确标出冲突；`abstain_reason` 非空。 | 拒答被视为正确结果。 |
| C5 低风险动作 | 建议写内部备注 | 用户确认后状态为 `completed`；相同幂等 Key 重放不重复写入。 | Action、Audit 与 Timeline。 |
| C6 高风险动作 | 涉及财务、权限或账户安全 | 必须先进入 `awaiting_approval`；管理员批准后才能 `resume`。 | `approval_id` 与 Wait/Resume Trace。 |
| C7 模型故障 | 关闭 Ollama、制造超时或非法 JSON | Rewrite 可降级，RAG 不返回 500，Debug 说明 fallback 原因。 | `fallback_reason` 与服务健康证据。 |
| C8 回归与回滚 | 运行原 Capstone E2E，并切回旧 Release | 原用例仍为 `pass`；回滚后版本一致，新能力按预期关闭或还原。 | 回归与回滚两份报告、Release Pointer。 |

Golden Set 应包含 6–8 条案例，并整体覆盖 C1–C8；一条案例可以覆盖多个验收标签。

## 6. 推荐验收指标

| 维度 | 指标 | 合格建议值 | 说明 |
|---|---|---:|---|
| 正确性 | 关键点通过率 | ≥ 80% | 适用于 6–8 条课程验收小样本。 |
| 证据 | 引用支持率 | 100% | citation 必须支持对应结论。 |
| 安全 | 高风险动作绕过数 | 0 | 一票否决项。 |
| 稳健性 | 模型故障请求成功率 | 100% | 允许降级，不允许返回 500。 |
| 回归 | 原 Capstone E2E | `pass` | 证明没有破坏既有产品链。 |
| 性能 | p95 延迟 | 报告并解释 | 不设跨机器统一阈值，但必须与基线同口径对比。 |

## 7. 必交证据检查

### 7.1 十二项能力证据

| 编号 | 要求 | 最低完成定义与证据 |
|---|---|---|
| R1 | 数据与契约 | ≥2 份合成文档、Manifest、字段/PII/版本校验；失败输入可被拒绝；提交 Contract Test 和失败报告。 |
| R2 | 幂等与版本 | 首次新增、二次跳过或 Upsert；数据和索引绑定 Release；提交两次运行计数。 |
| R3 | Query Rewrite | 错误码、型号、CVE、版本号不被删改；失败可降级；至少 1 条 Identifier Preservation Case。 |
| R4 | 检索与证据 | 使用 Hybrid Retrieval；返回 `evidence_id`、source、section；无证据不生成确定答案。 |
| R5 | 结构化输出 | 结果符合方案卡 Schema；字段缺失或类型错误可被检测；提交 Schema/契约测试。 |
| R6 | Skill/能力边界 | 能力用途、输入、输出、失败、权限和版本可发现。 |
| R7 | 受控动作 | 低风险需确认；财务、权限和账户安全动作走 HITL；幂等 Key 必填。 |
| R8 | 评测 | 6–8 条 Golden Set；基线和候选同口径；报告包含失败分布及原始结果。 |
| R9 | 可观测 | 关键链路可按 `trace_id` 关联；默认不记录敏感原文；提交 Phoenix Trace 和 Bad-case 分析。 |
| R10 | 发布回滚 | 提交版本绑定、门禁、激活/回滚证据；原 E2E 继续通过。 |
| R11 | 成本性能 | 记录 p50/p95、生成/降级比、平均 Token 或代理指标，并说明小样本限制。 |
| R12 | 生产差距 | 明确本地实现不等于完成高可用、容量和云安全；Reflection 至少列出 3 个下一步。 |

### 7.2 八项提交物

| 编号 | 提交物 | 最低内容 |
|---|---|---|
| D1 | README | 一键启动、前置条件、配置、验收命令、预期输出及故障排查。 |
| D2 | 设计说明 | 问题、用户、主链、边界、非目标和关键取舍；建议 2–4 页。 |
| D3 | 数据与契约 | 2 份以上文档、Manifest、结构化输出/Skill 契约；全部使用合成数据。 |
| D4 | 代码与测试 | 功能实现、契约测试、失败测试和原有回归；提交至个人分支。 |
| D5 | Golden Set | 6–8 条，整体覆盖 C1–C8，并包含预期证据、拒答及动作控制。 |
| D6 | 评测与 Trace | 基线/候选对比、原始结果、1 个 Bad-case 和 Phoenix `trace_id`。 |
| D7 | Release/回滚 | 版本绑定、门禁结果、激活/回滚步骤及回滚后验证。 |
| D8 | 演示与反思 | 8 分钟录屏或现场演示；Reflection 回答指定问题。 |

## 8. 可选加分

可选加分最多 **+10 分**，最终总分仍封顶 100 分。

| 加分项 | 分值 | 通过条件 |
|---|---:|---|
| GraphRAG | +2 | 为真正跨文档的问题设计路由，并用评测证明它比 Hybrid RAG 更合适。 |
| 多模态 | +2 | 新增图片、PDF 或音频证据，并保留可点击的 Evidence Anchor。 |
| 产品 UI | +2 | 在 Copilot Console 中实现清晰、可访问的方案卡和证据抽屉。 |
| 成本优化 | +2 | 在质量不下降的门禁下减少 Token、Rewrite 调用或 p95 延迟。 |
| 安全测试 | +2 | 增加 Prompt Injection、跨租户或工具滥用负例，并证明策略成功拦截。 |

## 9. 成绩解释

| 分数区间 | 结论 | 能力画像 |
|---:|---|---|
| 90–100 | 优秀 | 能把产品、数据、模型、控制、评测和发布连成可辩护的系统。 |
| 75–89 | 扎实 | 主链跑通、证据较全，少量非核心工程项仍可完善。 |
| 60–74 | 合格 | 完成核心能力与硬门槛，但评测、可观测或发布深度不足。 |
| <60 | 需补交 | 存在不可复现、无回归、缺少证据或关键链路断点。 |

> 成绩区间只在应用硬门槛规则后解释。G2、G3 或 G4 失败时，即使基础分达到 60 分，结论仍为“未通过”。

## 10. 教师验收与答辩

### 10.1 建议的 20 分钟答辩结构

| 环节 | 时间 | 教师动作 |
|---|---:|---|
| 产品演示 | 5 分钟 | 从 C1–C4 中随机指定两条，不允许只播放预录的成功路径。 |
| 代码导航 | 5 分钟 | 要求学员指出数据契约、RAG 主链、Tool 策略、评测和 Release 文件。 |
| 证据追踪 | 5 分钟 | 从一个 `trace_id` 追到 Rewrite/Retrieve/Generate/Action，并解释一个失败。 |
| 设计追问 | 5 分钟 | 围绕边界、取舍、生产差距和下一步提问。 |

### 10.2 建议追问

- 为什么这一步需要 LLM？若不用 LLM，确定性方案能做到什么程度？
- 为什么不把所有问题都交给 GraphRAG 或 Agent？路由依据是什么？
- 为什么拒答在这个案例中是成功，而不是失败？
- 如果错误码在改写中被删除，哪一层应发现？为什么不能只靠 Prompt？
- 哪个字段证明这是本机 Ollama 真生成，而不是 fallback？
- 谁有权批准高风险动作？租户和角色分别在哪一层验证？
- 所谓提升是否来自更换测试数据？基线和候选是否同口径？
- 一次回滚必须同时回滚哪些资产？只回滚服务代码会发生什么？
- 当前最不敢上线的是哪一部分？还缺少什么验收？

### 10.3 快速真实性检查

| 检查 | 现场操作 | 观察点 |
|---|---|---|
| 随机变体 | 替换一个版本号或错误码 | 改写仍保留标识，答案不是写死的。 |
| 关闭模型 | 停止 Ollama 或配置无效地址 | fallback 可解释，请求不返回 500。 |
| 重复动作 | 复用同一个 Idempotency Key | 不产生二次副作用。 |
| 越权尝试 | 普通坐席尝试批准高风险动作 | 策略拒绝并留下审计记录。 |
| 证据追溯 | 随机抽取一条 citation | 原文能支持对应结论。 |
| 回归抽查 | 现场运行原 E2E 或查看原始 JSON | `status=pass`，时间与 Commit 对应。 |
