# Reflection

## 1. 为什么不是普通聊天框

事实是输出被九字段契约约束，citation、动作策略、tenant 和 release 都由代码控制。我的判断是价值发生在“坐席是否可以依据证据采取下一步动作”的决策点，而不是把自然语言写得更像人。取舍是只支持 Webhook 小主题并最多三步；残余风险是复杂工单仍需人工诊断。下一步用处理时长和首次解决率验证业务收益。

## 2. 必须拒答或澄清的问题

缺产品/版本/错误码的“Webhook 不工作”必须澄清；知识库不存在的 `WS-QUANTUM-999` 必须拒答。否则模型会把通用 Webhook 建议包装成该精确代码的诊断，可能导致错误换钥、停机或安全事故。C3/C4 已把这两类风险变成回归门禁。

## 3. Query Rewrite 的收益和约束

确定性扩展加入根因、排查、恢复和验证词，扩大程序性语义召回；lexical query 保留版本与错误码。LLM 改写可能删改 `WS-WEBHOOK-409` 或新增不存在的标识，所以候选必须经过 protected-term、JSON、长度、租户缓存和超时门禁；本次 provider 400 时实际降级，原意未丢失。

## 4. 有引用仍可能失败

首轮 C4 就证明 citation 存在不等于支持结论：通用 Webhook 文档与未知代码语义相关，但没有出现该代码。评测同时核对 required source、abstain 和标识覆盖；修复后未知标识会清空引用。下一步应增加逐句 claim-evidence entailment，而不只检查 source slug。

## 5. 动作为什么仍需控制

内部备注虽低风险，也会污染工单时间线，所以需要用户确认和 idempotency key。财务补偿影响账务，审批不能只写在 Prompt；Prompt 可以被忽略、注入或产生非法 JSON。代码策略、RBAC、approval 状态机、审计和幂等共同形成不可绕过的边界。

## 6. 版本不一致的随机故障

新 Prompt 配旧索引可能要求不存在的字段；新 embedding 查询旧向量会降低召回甚至维度错误；新数据配旧 graph 会出现缺实体；新 Skill 配旧服务会建议不能执行的操作。表面上这些故障只在某些问题发生，像模型随机性，实际是版本撕裂。因此一个 manifest 和一个环境指针必须绑定全部组件。

## 7. Phoenix 中的坏案例

代表坏案例 C4 的首轮 trace `4256f7f0f6fbb532aede49123e2361ca`：retrieve 给出高相关通用文档，generate 没有证据覆盖门禁，最终未拒答。最小修复是在生成前逐字核对受保护标识，不修改向量模型或 Prompt；回归是 C4 和单测。残余风险是解析器漏掉图片/表格里的代码会保守拒答，因此下一步要增加 OCR/表格抽取覆盖测试。

## 8. 本地到生产的差距

- 安全：本地共享开发密钥和静态 demo 用户；生产需要 Secret Manager、短期凭证、细粒度 IAM、密钥轮换和独立审批人。
- 可靠性：单实例 Compose 无 HA；生产需要多副本、熔断/隔离、队列化长任务、备份恢复演练和跨区数据库。
- 容量：最终 8 条场景中 6 条在线方案卡请求的 p95 为 32.661 秒，不代表并发；生产需按 QPS、token、rerank 文档数做容量模型和压测。
- 运维：本地回滚后显式重启服务；生产需部署控制器监听 release pointer，自动协调镜像/配置、健康检查和渐进流量。

## 9. 再给两周先做什么

我会先做“离线逐句 citation entailment + 线上 unsupported-identifier/abstain 监控”，而不是增加更多动作。收益是直接降低 G2 假证据风险；风险是 judge 自身误判，因此先用人工标注小集校准；成本约一周构造 50–100 条 claim-evidence 样本、一周接入门禁和 dashboard。目标是 citation 支持率仍为 100%，同时把保守误拒率控制在人工标注集的 5% 以下。
