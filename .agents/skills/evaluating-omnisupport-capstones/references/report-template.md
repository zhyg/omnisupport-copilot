## 四段式作业报告（每次评估必交）

完整教师报告可以放在前面，但最终必须保留以下四段。`作业等级` 只能使用 `优秀`、`良好`、`不及格`；其余三个段落的可见正文分别不超过 1000 字，并在证据充分时各列 3–5 个独立要点。不得为了凑数重复拆分或编造观点。

```markdown
作业等级：<优秀/良好/不及格>

作业优点：
1. <正面观点>。依据：<具体实现、原始结果或实测命令>。对应：<评分项/Gate/C/D>。
2. ...

作业不足：
1. <观察事实>。依据：<文件行、原始 JSON 或实测命令结果>。影响：<对应 Gate/评分项>。
2. ...

改进方向：
1. <对应不足 1 的最小修复>。依据：<已证实不足及规则>。复验：<需要提交或运行的证据>。
2. ...
```

定稿前逐条执行证据复核：

1. 把优点、不足和改进方向中的复合句拆成可独立核验的原子观点，每个观点至少附一个直接依据。
2. 对每项不足主动搜索反证，包括后续 migration、其他调用路径、测试和继承资产。
3. 若仓库已有某项能力但学员没有提交个人运行证据，写“未提交/未验证”，不要写“系统没有/未实现”。
4. “未找到”必须注明检查范围，例如“在学员 Candidate 变更、README、eval 和 release 报告中未找到”。
5. 每项改进只解决一个已证实不足，并包含最小修复和可判定的复验标准；可选能力只能写成条件式建议。
6. 应用硬门槛后再确定等级。默认映射为：90–100 `优秀`，60–89 `良好`，低于 60、`需补交` 或 G2/G3/G4 导致的 `未通过` 均为 `不及格`。
7. 检查三个正文段落是否分别有 3–5 个独立要点；若直接证据不足，可以少于 3 个，并明确已检查的证据范围。

## 证据句式

优先使用：

> `<结论>`。代码在 `<路径:行号>` 只记录了 `<事实 A>`，但实际检索调用/SQL 缺少 `<事实 B>`；这不满足 `<规则>`。

正面观点也要举证：

> `<优点>`。`<路径:行号>` 由服务端强制 `<控制>`，且 `<测试命令>` 返回 `<结果>`；这满足 `<规则>`。

改进方向要回指不足并给出复验：

> 因 `<已证实不足及证据>`，应 `<最小修复>`；完成后以 `<测试/JSON/Trace 条件>` 验证。

避免使用：

> 看起来可能不安全，建议加强。

对不存在的证据，写清检查范围：

> 在提交目录的 README、baseline、eval、live evidence 和 release 报告中未找到 p50/p95 汇总；仅发现单条 rewrite latency。

不要写成无法证明的绝对结论：

> 项目完全没有性能数据。
